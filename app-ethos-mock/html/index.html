Despliegue en AWS + GitHub Actions

Publica esta aplicación en internet por HTTP detrás de un Application Load Balancer (DNS tipo *.elb.amazonaws.com), eligiendo ECS o Kubernetes (EKS), e incluye un pipeline de CI/CD con GitHub Actions.

Ethos te envía por correo el acceso AWS (IAM acotado) e invitación al repo. No hace falta dominio propio ni HTTPS para completar la prueba. Completa primero lo obligatorio; lo marcado como plus es voluntario y suma.

Uso de IA: puedes usar herramientas de inteligencia artificial para buscar métodos, documentación y procedimientos que te ayuden a resolver la prueba. No está permitido usar un agente de IA para que resuelva la prueba por ti (despliegue, configuración o entrega automatizada). Si se detecta este uso, no podrás continuar con tu proceso de selección.
Acceso AWS (obligatorio leer): tu usuario IAM solo puede crear y operar recursos etiquetados para ti. Sin los tags correctos, Create/Update/Delete fallarán (AccessDenied). No podrás listar clusters ECS/EKS de la cuenta ni operar clusters ajenos.

Tags en todo lo que crees (ECS, EKS, ECR, ALB, roles, etc.): ethos:candidate = <tu-id> (el que te enviamos por correo) ethos:project = devops-test Región: us-east-1 ECR: ethos-cand-<tu-id> (o ethos-cand-<tu-id>/...) Roles IAM: ethos-cand-<tu-id>-* No necesitas Route53 ni un dominio Ethos: la entrega usa el DNS público del ALB. No subas Access Keys al repo.

Cómo trabajar con tu IAM (consola vs CLI)

!

Roles IAM: créalos por CLI o IaC

En la consola de EKS/ECS es normal ver errores del tipo «No se pueden cargar los roles de IAM» / falta iam:ListRoles. No es un bloqueo de la prueba: crea el rol tú (CLI, Terraform, etc.) con el prefijo y el permissions boundary que te asignamos, y en la consola pega el ARN a mano.

Reglas al crear roles:

  • Nombre: ethos-cand-<tu-id>-... (ej. ...-eks-cluster, ...-ecs-exec)
  • Tag ethos:candidate=<tu-id>
  • Permissions boundary: arn:aws:iam::816583873447:policy/EthosDevOpsCandidateBoundary
  • Adjunta solo policies AWS managed necesarias (cluster EKS, nodos, task execution ECS, etc.)
# Ejemplo: rol de cluster EKS (ajusta <tu-id> y el trust policy) aws iam create-role \ --role-name ethos-cand-<tu-id>-eks-cluster \ --assume-role-policy-document file://eks-trust.json \ --permissions-boundary arn:aws:iam::816583873447:policy/EthosDevOpsCandidateBoundary \ --tags Key=ethos:candidate,Value=<tu-id> Key=ethos:project,Value=devops-test aws iam attach-role-policy \ --role-name ethos-cand-<tu-id>-eks-cluster \ --policy-arn arn:aws:iam::aws:policy/AmazonEKSClusterPolicy # En la consola EKS: pega el ARN del rol (no uses el desplegable)

Lo mismo aplica a roles de nodo EKS, task execution / task role de ECS: créalos por CLI/IaC y referencia el ARN. Preferible dejar esos JSON/HCL en el repo.

!

Clusters y listados

ecs:ListClusters y eks:ListClusters están denegados a propósito. Guarda el nombre del cluster/servicio que creaste y úsalo en CLI (describe, update-service, kubectl vía el cluster que tú provisionaste). No intentes inventariar la cuenta.

!

ECR con tags (obligatorio)

aws ecr create-repository \ --repository-name ethos-cand-<tu-id> \ --tags Key=ethos:candidate,Value=<tu-id> Key=ethos:project,Value=devops-test \ --region us-east-1

Sin esos tags, CreateRepository (y casi cualquier Create) fallará.

Elige un camino

Camino A — ECS

ECR + servicio ECS (p. ej. Fargate) + Application Load Balancer en HTTP.

Camino B — Kubernetes

Cluster (p. ej. EKS), Deployment/Service y exposición vía ALB (Ingress/LoadBalancer) en HTTP.

Tareas obligatorias

1

Local, rama y contexto Core

Clona el repo, crea una rama a partir de main con tu id de candidato y trabaja ahí (no en main). Entra a app-ethos-mock/, levanta Docker, confirma /health y /ready. Decide ECS o Kubernetes y documenta brevemente por qué.

git clone https://github.com/ethoscredito/ethos-devops-test.git cd ethos-devops-test git checkout main git pull git checkout -b candidato/<tu-id> cd app-ethos-mock docker compose up --build

Ejemplo de rama: candidato/christianmisel3. Validación local: http://localhost:8081 muestra esta guía.

2

Imagen en registry Core

Construye la imagen a partir del Dockerfile existente y publícala en ECR con nombre ethos-cand-<tu-id>, tags ethos:candidate / ethos:project, y una etiqueta de imagen trazable (commit SHA o semver).

3

Despliegue en el camino elegido Core

Deja la app corriendo en tu camino (ECS o Kubernetes). Debe responder en red privada o pública al menos en HTTP, con health checks alineados a /health y /ready.

Incluye en el repo (o PR) la definición del despliegue: task definition / service ECS, o manifiestos / Helm / Kustomize para Kubernetes. Preferible IaC o archivos versionados frente a clics solo en consola.

Si usas la consola: cuando pida roles IAM y no cargue el desplegable, pega el ARN del rol que creaste por CLI (sección de arriba). Tagea cluster, nodos, servicios y balanceadores con tus tags desde el primer create.

4

Exponer por HTTP en el ALB Core

Pon un Application Load Balancer (listener HTTP :80) delante de tu servicio ECS o de tu Ingress/Service en EKS. La URL de entrega es el DNS del ALB, por ejemplo http://….elb.amazonaws.com — sin dominio custom ni HTTPS obligatorio.

Validación (sustituye por tu DNS de ALB):

curl -s http://<tu-alb>.elb.amazonaws.com/health curl -s http://<tu-alb>.elb.amazonaws.com/ready

Debe responder OK desde internet. Tagea el ALB y target groups con tus tags.

5

CI/CD con GitHub Actions Core

Pipeline en .github/workflows/ que, como mínimo:

  • Construya la imagen Docker
  • La suba al registry
  • Despliegue (o actualice) el servicio en tu camino

Usa secretos/OIDC de forma segura. El workflow debe dispararse (o poder desplegar) desde tu rama candidato/<tu-id> (push a esa rama). No uses main para tu entrega. Deja evidencia de al menos una corrida exitosa en esa rama.

6

Entrega Core

Responde en el mismo hilo de correo de la prueba con:

  • Nombre de tu rama candidato/<tu-id> (o enlace al branch)
  • URL HTTP pública del ALB (http://….elb.amazonaws.com)
  • Enlace al workflow de Actions exitoso (en tu rama)
  • Resumen corto: camino, arquitectura, cómo gestionaste IAM/secretos
  • Plus realizados (si aplica)

Criterio de éxito mínimo: rama propia desde main + ALB HTTP + /health y /ready OK + pipeline que despliega.

Plus voluntarios

+

Ambos caminos Plus

Despliega también el camino que no elegiste como principal. Documenta ambas URLs de ALB (o cómo conviven). Ambos deben responder HTTP con health checks.

+

Automatizaciones a tu criterio Plus

Ejemplos (elige lo que aporte valor real; no hace falta hacerlos todos):

  • IaC completo (Terraform/CDK/CloudFormation) reproducible
  • Promoción por ambientes, rollback o blue/green / canary
  • Observabilidad (logs, métricas, alertas) y dashboards
  • Escaneo de imagen, políticas de red, least-privilege IAM
  • Documentación operativa (runbook) y etiquetado/costos

Se valora criterio, seguridad y claridad más que el volumen de herramientas.

Ethos provee: usuario IAM acotado por tags (solo tus recursos ECS/EKS), invitación al repo.
Evaluado provee: recursos con tags correctos, decisión de camino, registry + despliegue, ALB público en HTTP, GitHub Actions, y opcionalmente el segundo camino y automatizaciones plus (HTTPS/dominio pueden ir como plus).
